# 背包新增统计项适配说明

本文对应 MaaYuan 新增的符传、天机符传和顶部白金币统计，供库存服务与前端适配使用。事实来源是当前 `agent/items.json`、`PagedItemRecognition` 和库存报告生成代码；目标后端、前端仓库尚未在本次工作中检查，具体文件和实现方式需在各自仓库中确认。

目录源文件为 [agent/items.json](../agent/items.json)。`category` 是目录元数据，不随库存 entry 上报。识别用 PNG 与 NPZ 属于 MaaYuan 本地识别资源，服务端处理上报无需加载它们。

前端展示分组与上述目录元数据是两层含义：库存页应把符传、天机符传和白金币统一展示在

“货币”而隐藏它，也不得继续把白金币放入“鸟食礼包”。

## 2. 上报契约

本次继续使用 `myshare-inventory-exchange`、`version: 2`，现有 Schema 已能容纳新增道具 ID，无需提升协议版本。

| 字段 | 本次物品页扫描的值或规则 |
| --- | --- |
| `record_type` | `stock_snapshot`，数量为绝对库存 |
| `entity_type` | `item` |
| `snapshot_scope` | `listed`，只更新正文列出的道具 |
| `acquisition_channel` | `背包-物品`；旧报告中的 `背包-鸟食` 仍是有效渠道 |
| `entries[].id` | 使用上表稳定 ID，名称只用于展示 |
| `entries[].count` | 非负整数，显式 `0` 是有效库存值 |
| `account_id` | 自动上报使用 Token 绑定的子账号 ID |
| `record_id` | 一次扫描的稳定记录 ID，重试和补传不得重新生成 |
| `effective_at` | 保留客户端记录的扫描时间，用于现有库存基线规则 |

MaaYuan 实际调用 `GET /open-api/inventory/account` 查询绑定账号，随后通过 `POST /open-api/inventory/import` 上报完整 JSON，使用 `Authorization: Bearer <token>`。协议文档中的 `/v1/inventory/import` 是通用 HTTP 绑定建议；适配时保留当前服务的路由，不应据此更改客户端使用的 OpenAPI 路径。

正常扫描产生一条包含 7 个 entry 的物品快照。两种符传与四种鸟食通过背包格子识别；白金币在物品页扫描结束后从最后一张截图顶部读取。养成道具与密探心纸仍按原有分区记录。

扫描完成后，6 种格子道具中未识别到的条目由 MaaYuan 补为 `0`。白金币只有识别成功才加入记录：识别为 `0` 就上报 `0`，识别失败则整项省略，并继续保存或上报其余道具。接收方不得要求记录固定包含 7 项。

`listed` 更新应保留所有省略项的数量及对应库存基线，包括白金币和其他分区道具。快照不计入“今日获得”“累计获得”等奖励增量统计。既有白金币奖励仍按 `reward_delta` 处理，沿用协议中的时间与幂等规则。

## 3. 本地 TXT 导入

MaaYuan 的本地文件是带 UTF-8 BOM 的人类可读报告，可能含多条记录，并非上报 JSON 原文。样例由当前 `append_inventory_report` 直接生成。

记录底部的机器标记如下：

```text
#@MaaYInventoryRefV2 {"r":["myshare:73e8a2f249bb493c8a34d51e5c72d109"],"a":"acc_demo","s":"listed"}
```

- `r`：记录 ID 数组。本次单条物品快照只含一个 ID。
- `a`：子账号 ID，可省略。本地模式没有绑定账号时，导入流程应取得用户明确选择的目标账号，再形成满足 v2 要求的 record。
- `s`：快照范围，本次为 `listed`。

机器标记没有包含道具 ID 和数量，导入器需读取正文的时间、渠道、类型和道具行。已有 TXT 导入器的名称目录应增加“符传”与“天机符传”的精确映射，并复用“白金币”的现有映射；不能使用子串匹配，否则“天机符传”可能误归入“符传”。在线 JSON 始终直接使用稳定 ID。

同一份 TXT 与其自动上报记录应复用机器标记中的 `record_id`，由后端作幂等处理。文件内的“上报状态”只是说明文字，不替代服务端导入结果。导入界面应沿用现有账号选择、预览及提交流程。

## 4. 适配验收示例

在测试账号中验证以下行为；每个独立场景使用自己的记录 ID 和适当的时间。

| 场景 | 预期结果 |
| --- | --- |
| 当前符传为 100、天机符传为 80、白金币为 9000；导入比当前基线更新的样例 | 分别变为 2、19、3177；四种鸟食更新为样例值，其他道具保持原值 |
| 重复导入完全相同的样例，或自动上报后再导入对应 TXT | 作为重复成功处理，库存和奖励统计不再次变化 |
| 新快照只含 6 种格子道具，省略 `baijinbi` | 其余 6 项正常更新，白金币数量及其库存基线保持不变 |
| 新快照显式包含 `baijinbi: 0` 或某种符传数量为 0 | 对应库存更新为 0，界面保留有效零值 |
| 导入旧渠道 `背包-鸟食` 的四种鸟食快照 | 正常识别渠道；符传、天机符传、白金币保持原值 |
| 前端查看库存、分类筛选、搜索、导入预览和现有导出 | 两种符传与白金币分别可见，并统一位于“资源道具 → 抽卡资源”；目录元数据仍分别为“招募道具”和“货币”，名称和数量对应正确 |
| 查看导入当日的奖励获得量 | 本次快照不作为新增奖励计入统计 |

## 5. 实施范围

后端优先检查目录维护、名称映射、导入校验和现有库存读写链路；前端优先检查目录消费、分类、名称映射、导入预览及库存展示。已经符合上述契约的通用逻辑可直接复用。若目录在目标项目中通过种子数据或既有迁移管理，沿用该项目流程更新两个新条目即可。

本次新增项不要求单独的货币接口、账户余额字段或新的快照类型。前端可复用既有道具图标或默认占位图；仓库中的 `70×58` 背包模板是识别裁剪图，不是完整展示图标。
