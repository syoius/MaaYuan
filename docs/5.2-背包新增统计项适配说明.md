# 背包新增统计项适配说明

本文对应 MaaYuan 新增的符传、天机符传和顶部白金币统计，供库存服务与前端适配使用。事实来源是当前 `agent/items.json`、`PagedItemRecognition` 和库存报告生成代码；目标后端、前端仓库尚未在本次工作中检查，具体文件和实现方式需在各自仓库中确认。

## 2. 上报契约

本次继续使用 `myshare-inventory-exchange`、`version: 2`，现有 Schema 已能容纳新增道具 ID，无需提升协议版本。

| 字段 | 本次物品页扫描的值或规则 |
| --- | --- |
| `record_type` | `stock_snapshot`，数量为绝对库存 |
| `entity_type` | `item` |
| `snapshot_scope` | `listed`，只更新正文列出的道具 |
| `acquisition_channel` | `背包-物品`；旧报告中的 `背包-鸟食` 仍是有效渠道 |
| `entries[].id` | 使用上表稳定 ID，名称只用于展示 |
| `entries[].count` | 非负整数，显式 `0` 是有效库存值 |
| `account_id` | 自动上报使用 Token 绑定的子账号 ID |
| `record_id` | 一次扫描的稳定记录 ID，重试和补传不得重新生成 |
| `effective_at` | 保留客户端记录的扫描时间，用于现有库存基线规则 |

MaaYuan 实际调用 `GET /open-api/inventory/account` 查询绑定账号，随后通过 `POST /open-api/inventory/import` 上报完整 JSON，使用 `Authorization: Bearer <token>`。协议文档中的 `/v1/inventory/import` 是通用 HTTP 绑定建议；适配时保留当前服务的路由，不应据此更改客户端使用的 OpenAPI 路径。

扫描产生的物品快照最多包含 7 个 entry。两种符传与四种鸟食通过背包格子识别；白金币在物品页扫描结束后从最后一张截图顶部读取。养成道具与密探心纸仍按原有分区记录。

确认扫描完整后，6 种格子道具中未识别到的条目由 MaaYuan 补 0，游戏中用光后不显示的物品会归零；候选未确认或数量不可信的条目省略，不覆盖 Hub 原库存。白金币只有识别成功才加入记录：识别为 `0` 就上报 `0`，识别失败则整项省略，并继续保存或上报其余道具。没有可上报条目时跳过报告和上传，继续后续流程。接收方不得要求记录固定包含 7 项。

`listed` 更新应保留所有省略项的数量及对应库存基线，包括白金币和其他分区道具。快照不计入“今日获得”“累计获得”等奖励增量统计。既有白金币奖励仍按 `reward_delta` 处理，沿用协议中的时间与幂等规则。

### 背包识别诊断

「百宝箱 → 自动识别背包 → 背包识别诊断」默认选择「发送诊断截图（仅物品格区域）」，对物品、养成道具和心纸三个分区生效。只有配置连接码并启用同步到 YuanHub 时才发送；关闭或仅本地保存时不发送，下次背包扫描读取配置时删除本地待传背包诊断，不影响密探采集诊断。

`PagedItemRecognition` 正常确认到底或目标边界后，若 `tab1` 缺少天机符传或符传（候选未确认也算缺少），或任一分区有可疑数量，在库存保存、自动上报尝试结束后提交诊断；没有库存条目时跳过库存报告及上传，仍可提交诊断。中途失败、主动停止、达到页数上限但未确认边界时不提交。

模板识别对主阈值及备用阈值保留 `count_readings`，多位主结果成功时取值不变。按全局格检测 `page_conflict`（跨页主数量不同）、`threshold_disagree`（同帧成功阈值读数分歧）及 `edge_zone`（只在底部风险区读到）。风险区为中心距 ROI 底边 `[现有安全距离,150)`；养成页现有70px拒绝线保持不变。跨页冲突优先采用非风险区观测；非风险区仍冲突，或全在风险区且冲突时，数量不可信的条目省略，不覆盖库存，也不参与扫描完整后的缺失条目补 0；仅阈值分歧或仅风险区仍采用原主读数。界面仅汇总可疑格及跳过名称，每格各次读数、原因、取值写入 `console=False` 日志。

扫描在内存暂存最多30页 action `roi` JPEG，单张≤512KiB，不缩放、不含顶栏。结束时优先选可疑格所在页；漏扫补入前12页，合计最多12张并重编号；无图片引用的读数和空格条目丢弃。无法保存应保留页、尺寸变化或最低质量仍超限时放弃整包诊断，不影响库存任务。

沿用 `schema_version=1`、`feature=inventory_bag_scan`、`outcome=data_review`、`catalog.source=builtin`（索引SHA-256前16位）。issues最多2条：原 `bag_item_missing/bag_tab1` 不变；新增 `bag_count_suspect`，stage 为 `bag_tab1`、`bag_tab3_1`、`bag_tab3_2`，reason 为上述单一原因或 `mixed`。有数量issue时顶层 `bag_cells` 必填（1–64格），issue.count等于格数；每格仅含 `entity_type/entity_id/chosen/reasons/readings`，chosen可为null。每格1–8条读数仅含 `image_index/count_box/count/raw/score/source`：数字0–99999999或null，raw为0–8位数字，score保留3位小数，source为primary/fallback；count_box仍为整帧坐标并须落在原分辨率内。只发送ID、数字、坐标，不附OCR原文或日志。manifest上限64KiB，按格顺序截掉末尾超限条目并同步修正count/reason，另为intent图片描述预留2KiB。

复用诊断后台worker与凭证绑定、7天/20包/20MiB待传上限，队列仍为 `debug/toolbox_diagnostics/inventory_bag_scan/pending`；网络失败在后续正常完成任一背包分区时重试。失败写 `console=False` 日志，不改变action结果、不等待后台上传。YuanHub须部署扩展契约；旧服务拒收则放弃该包，密探场景保持原有规则。

「背包调试截图」默认关闭；选择「保存每页截图和读数到 debug/bag-count」时，仅覆盖「背包调试截图配置」的 `attach.debug_page_dir`。Action自身未指定 `debug_page_dir` 时读取该配置，并按 `snapshot_list.name` 拼接 `tab1`、`tab3-1`、`tab3-2` 子目录；读取失败按关闭处理，不覆盖识别参数。每次运行输出完整PNG、含备选读数的 `page-XX.json` 及含可疑格的 `collected.json`。完整PNG可能含顶栏，仅保存本地，不随诊断上传。

## 3. 本地 TXT 导入

MaaYuan 的本地文件是带 UTF-8 BOM 的人类可读报告，可能含多条记录，并非上报 JSON 原文。样例由当前 `append_inventory_report` 直接生成。

记录底部的机器标记如下：

```text
#@MaaYInventoryRefV2 {"r":["myshare:73e8a2f249bb493c8a34d51e5c72d109"],"a":"acc_demo","s":"listed"}
```

- `r`：记录 ID 数组。本次单条物品快照只含一个 ID。
- `a`：子账号 ID，可省略。本地模式没有绑定账号时，导入流程应取得用户明确选择的目标账号，再形成满足 v2 要求的 record。
- `s`：快照范围，本次为 `listed`。

机器标记没有包含道具 ID 和数量，导入器需读取正文的时间、渠道、类型和道具行。已有 TXT 导入器的名称目录应增加“符传”与“天机符传”的精确映射，并复用“白金币”的现有映射；不能使用子串匹配，否则“天机符传”可能误归入“符传”。在线 JSON 始终直接使用稳定 ID。

同一份 TXT 与其自动上报记录应复用机器标记中的 `record_id`，由后端作幂等处理。文件内的“上报状态”只是说明文字，不替代服务端导入结果。导入界面应沿用现有账号选择、预览及提交流程。

## 4. 适配验收示例

在测试账号中验证以下行为；每个独立场景使用自己的记录 ID 和适当的时间。

| 场景 | 预期结果 |
| --- | --- |
| 当前符传为 100、天机符传为 80、白金币为 9000；导入比当前基线更新的样例 | 分别变为 2、19、3177；四种鸟食更新为样例值，其他道具保持原值 |
| 重复导入完全相同的样例，或自动上报后再导入对应 TXT | 作为重复成功处理，库存和奖励统计不再次变化 |
| 新快照只含 6 种格子道具，省略 `baijinbi` | 其余 6 项正常更新，白金币数量及其库存基线保持不变 |
| 新快照显式包含 `baijinbi: 0` 或某种符传数量为 0 | 对应库存更新为 0，界面保留有效零值 |
| 导入旧渠道 `背包-鸟食` 的四种鸟食快照 | 正常识别渠道；符传、天机符传、白金币保持原值 |
| 前端查看库存、分类筛选、搜索、导入预览和现有导出 | 两种符传与白金币分别可见，并统一位于“资源道具 → 抽卡资源”；目录元数据仍分别为“招募道具”和“货币”，名称和数量对应正确 |
| 查看导入当日的奖励获得量 | 本次快照不作为新增奖励计入统计 |

## 5. 实施范围

后端优先检查目录维护、名称映射、导入校验和现有库存读写链路；前端优先检查目录消费、分类、名称映射、导入预览及库存展示。已经符合上述契约的通用逻辑可直接复用。若目录在目标项目中通过种子数据或既有迁移管理，沿用该项目流程更新两个新条目即可。

本次新增项不要求单独的货币接口、账户余额字段或新的快照类型。前端可复用既有道具图标或默认占位图；仓库中的 `70×58` 背包模板是识别裁剪图，不是完整展示图标。
