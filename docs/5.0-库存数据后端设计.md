# 库存与奖励数据后端设计

本文供后端开发人员参考。跨平台 JSON 的字段定义、示例和兼容规则见 [库存数据交换协议 v2](./5.1-库存数据交换协议-v2.md)。

## 1. 设计结论

系统只维护两类事实：

- `inventory_account`：用户自行创建的游戏子账号；每个子账号拥有独立库存和流水。
- `current_stock`：子账号当前库存，是可被完整背包快照覆盖的状态。
- `reward_delta`：一次奖励带来的增量流水，仅用于幂等上报、延迟上报处理和历史统计。

不要在库存文档中维护 `acquired` 或 `total_acquired`。周、月、任意时间段的获得量均按需聚合 `reward_delta`；历史流水也不得在每次读取库存时重新累加。

```text
奖励上报 ──保存流水──> inventory_records ──按需聚合──> 时段获得量
    │
    └──晚于相应库存基线──> current_stock += count

背包快照 ───────────────────────────────> 覆盖或更新 current_stock

所有箭头均限定在同一个 `(user_id, account_id)` 内。
```

新后端可以复用现有 MongoDB 与用户系统，并使用自己的 collections。Redis 不是事实来源，初期也不是必需组件。

## 2. 术语

| 术语             | 含义                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------ |
| `item`           | 普通道具。                                                                           |
| `agent`          | 角色关联物品。                                                                       |
| `reward_delta`   | 奖励增量；`count` 必须大于 0。                                                       |
| `stock_snapshot` | 某时刻读取到的绝对库存；`count` 可以为 0。                                           |
| `full` 快照      | 覆盖该用户、该 `entity_type` 的完整库存；未列出的对象视为 0。                        |
| `listed` 快照    | 只覆盖列出的对象；未列出的对象保持不变。                                             |
| 库存基线         | 最近一次对某个对象具有权威性的快照时间。延迟到达且不晚于基线的奖励不再增加当前库存。 |

## 3. 用户身份边界

- 在线 API 从现有登录态或访问令牌取得内部 `user_id`，不接受客户端在正文中声明内部用户 ID。
- 用户可以在自己的登录身份下创建、改名和删除子账号。`account_id` 创建后不可修改或复用，显示名称可以修改。
- v2 上报的每条 record 必须声明 `account_id`，且该账号必须属于当前 `user_id`。正文不得借此访问其他用户的账号。
- 用户手动导入 v2 文件时，前端先让用户把文件账号映射到已有子账号，或明确确认创建缺少的账号；提交给库存写入逻辑的 record 必须已经换成目标 `account_id`。自动上报不得创建账号，引用不存在账号时返回 `unknown_account_id`。不得按名称静默合并。
- 合作平台的外部账号映射由认证/绑定层维护，交换协议本身不携带 MyShare 内部用户 ID。
- 新后端只需读取用户身份，并读写自己的库存 collections；不应修改原有用户资料。

### 3.1 `inventory_accounts`

```javascript
{
  _id: ObjectId("..."),
  user_id: ObjectId("..."),
  account_id: "acc_01J...",
  name: "大号",
  created_at: ISODate("2026-08-17T02:00:00Z"),
  updated_at: ISODate("2026-08-17T02:00:00Z")
}
```

`account_id` 是协议中的用户范围稳定 ID，由服务端生成 1–64 字符；前端只展示和编辑 `name`。建立 `{ user_id: 1, account_id: 1 }` 和 `{ user_id: 1, name: 1 }` 两个唯一索引。账号读取、改名和删除必须同时匹配 `account_id` 与 `user_id`。

删除子账号表示删除该账号本身、`inventory_current` 和 `inventory_records` 中的全部数据。前端必须明确提示库存与历史也会删除；后端在一个 transaction 中完成三处删除。当前规模不需要软删除或恢复机制。

## 4. MongoDB collections

下面是推荐结构，不要求字段顺序完全一致。

### 4.1 `inventory_current`

每个子账号、每种 `entity_type` 一个文档：

```javascript
{
  _id: "<user-id>:<account-id>:item",
  user_id: ObjectId("..."),
  account_id: "acc_01J...",
  entity_type: "item",
  full_baseline_at: ISODate("2026-08-16T02:30:00Z"),
  entries: {
    baijinbi: {
      count: NumberLong(103),
      listed_baseline_at: null
    },
    baimozhijiu: {
      count: NumberLong(25),
      listed_baseline_at: ISODate("2026-08-16T03:00:00Z")
    }
  },
  updated_at: ISODate("2026-08-16T03:00:01Z")
}
```

约定：

- 对象的有效基线为 `max(full_baseline_at, listed_baseline_at)`。
- 完整快照替换 `entries` 并更新 `full_baseline_at`；未列出的对象归零，可直接不保留其键。
- `listed` 快照只替换正文列出的对象，并更新这些对象的 `listed_baseline_at`。
- 奖励增量使用 `$inc` 修改 `entries.<entity_id>.count`，但不改变快照基线。
- 对象名称不必复制到该文档；展示名称来自统一对象目录。

当前数量和 ID 都很有限，一个子账号一种类型一个文档可获得简单的读取和单文档原子更新。所有读取和写入必须同时限定 `user_id`、`account_id` 和 `entity_type`。若未来单个子账号的对象数量接近 MongoDB 文档大小限制，再改为每个对象一个文档；当前没有必要预先拆分。

### 4.2 `inventory_records`

保存已接收的交换记录：

```javascript
{
  _id: ObjectId("..."),
  record_id: "myshare:7f75b99e98834590a0aca3634e8fab5d",
  user_id: ObjectId("..."),
  account_id: "acc_01J...",
  record_type: "reward_delta",
  entity_type: "agent",
  acquisition_channel: "派遣",
  effective_at: ISODate("2026-08-16T02:10:00Z"),
  received_at: ISODate("2026-08-16T02:10:03Z"),
  producer: {
    platform: "myshare",
    version: "5"
  },
  entries: [
    { id: "char_105_simahui", count: NumberLong(2) },
    { id: "char_029_xiuqiu", count: NumberLong(1) }
  ],
  stock_effect: "applied"
}
```

`stock_effect` 推荐值：

- `applied`：奖励已经增加当前库存，或快照已经更新当前库存。
- `history_only`：记录已保存，但因为不晚于库存基线而未改变当前库存。
- `superseded`：旧快照已保存，但比当前快照更早，未覆盖当前库存。

这些状态用于排查导入结果，不参与业务计算。

索引：

```javascript
db.inventory_records.createIndex(
  { user_id: 1, account_id: 1, record_id: 1 },
  { unique: true },
);
db.inventory_records.createIndex({ user_id: 1, account_id: 1, effective_at: 1 });
db.inventory_records.createIndex({
  user_id: 1,
  account_id: 1,
  record_type: 1,
  effective_at: 1,
});
```

周/月统计只查询 `record_type: "reward_delta"`，再 `$unwind` 和 `$group`。普通 collection 已足够；无需为当前规模引入 MongoDB time series collection。

### 4.3 对象目录

跨平台主键为 `(entity_type, entity_id)`：

- `item` 的 ID 和中文名来自 `agent/items.json` 的 `id` / `name`。
- `agent` 的跨平台 ID 使用 `agent/operators.json` 的正式 `id`，例如司马徽为 `char_105_simahui`。识别模板使用的拼音 `item_id` 只用于本地匹配，不作为角色跨平台主键。

后端可以建立 `entity_catalog` collection，也可以在部署时将这两个文件转换后载入。中文名是展示信息，不得用中文名代替稳定 ID 做数据库主键。

建议提供只读接口：

```http
GET /v1/inventory/catalog
```

返回目录版本以及所有 `{ entity_type, id, name }`，供合作平台建立映射。目录版本使用发布版本或日期即可，不需要计算内容哈希。

## 5. 写入规则

### 5.1 通用校验

收到一份交换文档后：

1. 验证 JSON Schema 和协议版本。
2. 通过认证上下文确定 `user_id`。
3. 若携带 `accounts`，验证其中的 ID 没有重复；无论是否携带目录，都按 `(user_id, record.account_id)` 验证对应账号存在。客户端名称不参与匹配或写入。
4. 验证 `(entity_type, id)` 存在于对象目录。
5. 验证同一 record 的 `entries` 中没有重复 ID。
6. 同一批记录按 `account_id` 分组，各组按 `effective_at` 升序处理；相同时间先处理 `reward_delta`，后处理 `stock_snapshot`，让快照成为最终权威值。
7. 同一用户、同一子账号的 `record_id` 已存在时按重复记录返回成功，不再更新库存。
8. 同一用户、同一子账号的 `record_id` 已存在但正文不同，返回 `record_conflict`，不得覆盖原记录。不同子账号或不同用户的相同 `record_id` 互不影响。

同一份本地文件可以安全地重复导入。

### 5.2 奖励增量

对每个 entry 计算相应对象的有效库存基线：

```text
baseline = max(full_baseline_at, entries[id].listed_baseline_at)
```

- 没有基线，或 `effective_at > baseline`：保存流水并 `$inc` 当前库存。
- `effective_at <= baseline`：保存流水用于统计，但设置 `stock_effect: history_only`，不修改当前库存。

例：10:10 获得 `+5`，10:30 背包快照已经包含这 5 个，但奖励文件 11:00 才导入。该奖励仍属于历史统计，但不得再次增加当前库存。

同一记录含多个 entry 时，`inventory_records` 插入和 `inventory_current` 更新应放在同一个 MongoDB transaction 中。MongoDB 单文档更新本身是原子的；跨 collection 保持一致时才需要 transaction。

### 5.3 库存快照

- `full`：当快照不早于当前完整快照时，更新 `full_baseline_at`。对于 `listed_baseline_at` 不晚于本快照的对象，使用完整快照值（未列出则归零）；对于拥有更晚 `listed_baseline_at` 的对象，保留其更新值，避免较旧的完整快照覆盖较新的局部读取。
- `listed`：只设置列出的绝对数量，并更新对应 `listed_baseline_at`。
- 比现有相应基线更早的快照只存档，设置 `stock_effect: superseded`。
- 生产者必须给出截图实际完成或数据实际读取的时间，不能用之后的文件导入时间代替。

批量导入会先按时间排序，因此“历史奖励 + 最新库存快照”能够得到正确的最终库存。跨多个独立请求发送时，合作平台应先发送较早记录；后端仍需按照基线规则处理延迟到达的记录。

### 5.4 幂等与事务

`record_id` 是幂等键。推荐一次 transaction 完成：

1. 插入 `inventory_records`。
2. 更新 `inventory_current`。
3. 提交。

同一用户、同一子账号的重复 `record_id` 不算失败，响应中计入 `duplicates`。MongoDB transaction 需要 replica set 或 sharded cluster；若当前实例是 standalone，应先确认部署条件，而不是使用 Redis 代替持久幂等。

## 6. 查询与统计

当前库存直接读取 `inventory_current`，不扫描历史流水。

任意时段获得量：

```javascript
db.inventory_records.aggregate([
  {
    $match: {
      user_id: userId,
      account_id: accountId,
      record_type: "reward_delta",
      effective_at: { $gte: start, $lt: end },
    },
  },
  { $unwind: "$entries" },
  {
    $group: {
      _id: {
        entity_type: "$entity_type",
        entity_id: "$entries.id",
      },
      acquired_count: { $sum: "$entries.count" },
    },
  },
]);
```

所有区间使用 `[start, end)`，服务端根据用户时区把“本周/本月”转换为 UTC 边界。`acquired_count` 只出现在统计响应里，不写回库存文档。普通查询必须指定一个 `account_id`；跨账号汇总只用于明确的“全部账号”视图，且响应必须保留账号分组，不把数量合并成一个虚构库存。

## 7. Redis 的职责

第一版可以完全不使用 Redis。MongoDB 中每个用户的当前库存只有一两个文档，直接读取已经很轻。

确实出现热点后，Redis 只用于：

- 缓存指定子账号的 `current_stock` 查询结果；库存变更后删除对应 `(user_id, account_id)` key。
- 缓存指定子账号、指定时间范围的统计结果；新增奖励流水后删除对应 `(user_id, account_id)` 的统计缓存。

不要把 Redis 作为唯一的幂等记录、库存源或奖励流水源。Redis Streams 也不是当前同步写入流程的必要组件。

## 8. 推荐 HTTP 接口

```text
POST   /v1/inventory/accounts
GET    /v1/inventory/accounts
PATCH  /v1/inventory/accounts/{account_id}
DELETE /v1/inventory/accounts/{account_id}
POST /v1/inventory/import
GET  /v1/inventory/export?account_id=...&include=current,rewards&from=...&to=...
GET  /v1/inventory/export?scope=all&include=current,rewards&from=...&to=...
GET  /v1/inventory/current?account_id=...&entity_type=item
GET  /v1/inventory/records?account_id=...&entity_type=item&from=...&to=...
DELETE /v1/inventory/records/{record_id}?account_id=...
GET  /v1/inventory/acquired?account_id=...&entity_type=item&from=...&to=...
GET  /v1/inventory/catalog
```

创建账号正文只需要 `{ "name": "大号" }`，响应返回服务端生成的 `{ "id", "name" }`。改名正文同样只包含 `name`。账号列表供前端下拉选择；非技术用户不需要手写或记忆 `account_id`。

除 `catalog` 外，所有单账号读写接口都必须验证 `account_id` 属于当前登录用户。导出必须且只能指定 `account_id` 或 `scope=all` 之一。删除单条流水后仅重放对应子账号的剩余记录，不得重建或锁定该用户的其他子账号。

`POST /import` 与本地文件导入必须调用同一套校验和写入逻辑。建议响应：

```json
{
  "accepted": 2,
  "duplicates": 1,
  "history_only": 1,
  "superseded": 0
}
```

推荐错误：

| HTTP    | code                         | 含义                                  |
| ------- | ---------------------------- | ------------------------------------- |
| 400     | `invalid_json`               | JSON 无法解析。                       |
| 401/403 | `unauthorized` / `forbidden` | 未登录或无权为目标账号导入。          |
| 404     | `account_not_found`          | 子账号不存在或不属于当前用户。        |
| 409     | `record_conflict`            | 相同 `record_id` 已存在，但内容不同。 |
| 409     | `account_name_conflict`      | 当前用户已有同名子账号。              |
| 422     | `schema_validation_failed`   | 字段或类型不符合协议。                |
| 422     | `unknown_account_id`         | 导入文档引用了当前用户不存在的账号。  |
| 422     | `unknown_entity_id`          | 对象目录中不存在该 ID。               |
| 422     | `unsupported_version`        | 不支持该协议 major version。          |

建议先完整校验一份导入文档，再开始写入；格式错误时整份拒绝，避免用户不知道哪些条目已经生效。

## 9. MaaYuan/MyShare 识别报告映射

`AgentItemRecognition` 和 `PagedItemRecognition` 已输出协议所需字段：

| 识别报告                      | 协议字段                                       |
| ----------------------------- | ---------------------------------------------- |
| `invocation_id`               | `record_id`，建议加 `myshare:` 前缀。          |
| 前端当前选择的子账号 ID       | `account_id`。                                 |
| `timestamp`                   | `effective_at`。                               |
| `entity_type`                 | `entity_type`。                                |
| `item_id`                     | 当 `entity_type=item` 时写入 `entries[].id`。  |
| `operator_id`                 | 当 `entity_type=agent` 时写入 `entries[].id`。 |
| `item_name` / `operator_name` | `entries[].name`。                             |
| `count`                       | `entries[].count`。                            |
| `acquisition_channel`         | record 级 `acquisition_channel`。              |

同一次 `invocation_id` 的行先取得前端当前选择的稳定 `account_id`，再转换为规范 ID：普通道具取 `item_id`，角色取 `operator_id`；然后按 `(entity_type, 规范 ID)` 分组求和并生成 `reward_delta`。未明确选择账号时不得上传，避免把库存写入错误账号。识别分数、ROI、行列和模板路径是本地诊断数据，不进入跨平台协议。

背包扫描只有在确认覆盖范围后才能生成快照：完整扫描生成 `snapshot_scope: full`；仅识别局部页面时生成 `snapshot_scope: listed`。

## 10. 验收用例

后端至少应验证以下行为：

1. 同一账号的同一 `record_id` 导入两次，只增加一次库存。
2. 同一账号的同一 ID、不同正文返回冲突。
3. 奖励晚于快照时增加库存。
4. 奖励早于或等于快照时只进入历史统计。
5. `full` 快照使未列出的旧库存归零。
6. `listed` 快照不影响未列出的库存。
7. 最新快照覆盖此前已经应用的奖励，历史统计仍能查到这些奖励。
8. `item` 与 `agent` 的相同 ID 互不冲突。
9. 同一文件重复导入的响应可解释且最终库存不变。
10. 月/周查询只聚合 `reward_delta`，不聚合快照。
11. 两个子账号使用相同 `record_id` 时分别生效，库存、基线和统计互不影响。
12. record 缺少 `account_id`、引用未声明账号或引用不属于当前用户的账号时，整份导入不产生写入。
13. 改名后原库存仍属于同一个 `account_id`。
14. 删除流水只重放该流水所属子账号。
15. 单账号导出只含指定账号；全部导出保留各 record 的账号归属，重新导入后不会混库。
16. 删除子账号会删除该账号库存和历史，不影响同一用户的其他子账号。

## 11. 从单账号模型迁移

部署 v2 数据结构前，为每个已有库存或流水的用户创建一个名为“默认账号”的 `inventory_accounts` 文档，并把生成的 `account_id` 写入该用户全部 `inventory_current` 和 `inventory_records`。随后按新键重建索引，并把 `inventory_current._id` 改为包含 `account_id` 的形式。

迁移完成后再启用要求 `account_id` 的写入接口，避免迁移期间产生无账号的新记录。旧 v1 文件没有子账号归属，只允许用户在导入界面明确选择一个目标子账号；服务端转换时给所有 records 填入该账号 ID。不要根据文件中的展示名称推断目标账号，也不要创建长期双写或双读兼容层。
