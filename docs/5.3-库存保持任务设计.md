# 库存保持任务设计

「库存保持」根据勾选的修为套数和兵书人份补齐库存。简中、繁中的任务队列均使用同一个 Python 动作 `InventoryMaintenance`，由它调用百宝箱的背包扫描和现有历练任务。

## 调用顺序

1. 四项资源各有一个开关，开关下方始终显示套数或人份。关闭时保留数量，再次开启沿用上次选择。只为已开启的资源计算目标，全部关闭时直接结束。
2. 从选定来源读取当前账号的库存，按物品 ID 保留数量和盘点时间。明确记录为 0 表示已知零库存。缺少可用基线的物品标为未知。
3. 若判断目标还缺数据，且勾选了「读不到所选资源的库存时，允许识别背包」，调用一次现有的 `背包识别-start`。沿用百宝箱的扫描配置，在养成道具分区完成后结束，读取本次成功扫描生成的库存快照。补扫后重新判断全部所选目标。仍无法判断的组单独跳过，继续处理其他组。
4. 按面板顺序处理风火、地水、阴阳和经验。每次取下一批需要执行的关卡和次数，通过 `context.run_task(现有入口, 本批选项覆盖)` 执行，结算后重新计算剩余缺口。

## 接现有库存来源

| 来源 | 接法 |
| --- | --- |
| 本地报告 | 自动查找程序目录下的 `StockReport*.txt` 和 `DailyRewards*.txt`，合并同一账号的 V2 快照和后续奖励。已有报告后缀的配置沿用该后缀。发现多个账号且无法确定归属时按缺数据处理。 |
| YuanHub 云库存 | 用连接码读取绑定账号的 `entries`，结算后同步奖励。读库存需要 `inventory:read`，同步奖励需要 `inventory:write`。全量盘点按协议处理被归零的物品，局部盘点只采用有依据的数量。 |
| 允许补扫 | 调用 `背包识别-start`，只扫描养成道具页。读取此次调用单独生成的快照并写入当前账号报告。扫描器判为不确定的物品保留为未知。账号未能确定时，此次记录单独保存在 `data/inventory-maintenance/unassigned`。 |

读取失败、权限不足或关键材料没有数量，都沿用第 3 步。能确定已经达标的项目直接跳过。例如，已知两种兵书的经验已经足够，第三种兵书读数缺失也无需开背包。

## 接现有历练任务

| 目标 | 计算与调用 |
| --- | --- |
| 风火、地水、阴阳修为 | 每套六档依次需要 180、570、1440、2550、3420、2100。每档计算 `max(0, 套数 × 单套用量 − 库存)`。沿用 YuanHub 的层数分配规则，在 MaaYuan 支持且本账号可扫的层数中分配次数，同时抵扣一关的两种产出。把类别、级别、指定次数传给 `刷修为历练启动`。 |
| 兵书经验 | 残卷、全卷、六韬兵书分别按 100、1,000、10,000 折算。缺少的经验除以可扫档位的单次必得经验，向上取整。把级别、指定次数传给 `刷经验历练启动`。 |

子任务复用 `interface.json` 的类别、关卡和「历练奖励配置」。修为按 YuanHub 的 `trainingSchedule` 比较正序与倒序分配。一次只需刷同一层便能补齐所有缺口时，总次数相同则优先该层，减少进出菜单的次数。

进入扫荡设置后读取游戏实际显示的次数。「最多」可以超过 6 次。任务按库存缺口、本轮该类剩余额度（每类 6 次）和可用体力自动减少次数，每点一次减号就核对一次新读数。当游戏次数用完时结束该类，体力不足以扫一次时结束本次任务。

## 结算与验收

点击前，把批次 ID 和涉及的材料写入本地。确认「扫荡结果」后，按照实际次数和必掉表写一条奖励记录。使用 YuanHub 云库存时，把同一记录上传到已验证的子账号。重试复用原记录 ID。上报失败时保留本地报告并显示补传入口。背包补扫的快照用于本地计算。本地重跑按记录 ID 去重，云库存仍与原读数一致时可接续本机已确认的结算。结算中断后，受影响材料需要更新的盘点记录才能继续刷取。

- 四项目标已达标时，背包和历练子任务的调用次数均为 0。
- 云端缺少两个组的数据时，关闭补扫只跳过这两个组；开启补扫最多打开一次背包。
- 风火只缺翠扇 70、金丝扇 80 时，第 6 层每次掉 40、30。额度足够则扫 3 次，只剩 2 次则扫 2 次并报告剩余缺口。
- 切换账号、重复启动、扫荡后中断时，分别验证账号隔离、已确认收益去重，以及结算未知时不会盲目重复扫荡。
