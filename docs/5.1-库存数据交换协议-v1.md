# 库存数据交换协议 v1

本文定义 MyShare 与合作平台之间导入、导出库存和奖励记录时使用的 JSON 格式。机器可读约束见 [inventory-exchange-v1.schema.json](./schema/inventory-exchange-v1.schema.json)。

## 1. 协议目标

- 同一个 JSON 文件既可用于用户本地导入，也可作为服务端 API 正文。
- 区分绝对库存和奖励增量，避免重复累加。
- 同一文件可重复提交而不改变结果。
- 使用稳定 ID 对齐不同平台；中文名称只用于展示。
- 不传递平台内部用户 ID。用户归属由登录态、账号绑定或导入操作确定。

协议不包含 OCR 分数、截图坐标、模板路径、设备信息等本地诊断数据。

## 2. 完整示例

```json
{
  "format": "myshare-inventory-exchange",
  "version": 1,
  "exported_at": "2026-08-16T11:30:00+08:00",
  "catalog_version": "2026-08-16",
  "producer": {
    "platform": "myshare",
    "version": "5"
  },
  "records": [
    {
      "record_id": "myshare:7f75b99e98834590a0aca3634e8fab5d",
      "record_type": "reward_delta",
      "entity_type": "agent",
      "effective_at": "2026-08-16T10:10:00+08:00",
      "entries": [
        { "id": "char_105_simahui", "name": "司马徽", "count": 2 },
        { "id": "char_029_xiuqiu", "name": "绣球", "count": 1 }
      ]
    },
    {
      "record_id": "partner-a:018f83b8-2aba-7b50-a03b-cc4e271789cd",
      "record_type": "stock_snapshot",
      "entity_type": "item",
      "effective_at": "2026-08-16T10:30:00+08:00",
      "snapshot_scope": "full",
      "entries": [
        { "id": "baijinbi", "name": "白金币", "count": 103 },
        { "id": "baimozhijiu", "name": "百末旨酒", "count": 25 }
      ]
    }
  ]
}
```

## 3. 顶层字段

| 字段                | 必填 | 类型              | 说明                                        |
| ------------------- | ---- | ----------------- | ------------------------------------------- |
| `format`            | 是   | string            | 固定为 `myshare-inventory-exchange`。       |
| `version`           | 是   | integer           | 当前为 `1`。                                |
| `exported_at`       | 是   | RFC 3339 datetime | 文件或请求正文生成时间，不参与库存计算。    |
| `producer`          | 是   | object            | 生成数据的平台。                            |
| `producer.platform` | 是   | string            | 平台稳定短名称，如 `myshare`、`partner-a`。 |
| `producer.version`  | 否   | string            | 平台或客户端版本，仅用于排查问题。          |
| `catalog_version`   | 否   | string            | 生成方使用的对象目录版本。                  |
| `records`           | 是   | array             | 一条或多条库存/奖励记录。                   |

同一份文档只属于一个用户，但正文没有 `user_id`：

- 在线上传：由访问令牌确定用户。
- 用户导入文件：归属于当前登录用户。
- 平台间服务调用：由事先建立的外部账号绑定确定用户。

## 4. Record 字段

| 字段             | 必填     | 类型              | 说明                                                                                               |
| ---------------- | -------- | ----------------- | -------------------------------------------------------------------------------------------------- |
| `record_id`      | 是       | string            | 在一个用户的数据集中唯一的幂等 ID，1–128 字符。建议使用 `<platform>:<uuid>` 使其实际达到全局唯一。 |
| `record_type`    | 是       | enum              | `reward_delta` 或 `stock_snapshot`。                                                               |
| `entity_type`    | 是       | enum              | `item` 或 `agent`。一条 record 不能混合两种类型。                                                  |
| `effective_at`   | 是       | RFC 3339 datetime | 奖励发生时间或库存实际读取时间。必须带 `Z` 或 UTC offset。                                         |
| `snapshot_scope` | 快照必填 | enum              | `full` 或 `listed`；奖励记录不得携带。                                                             |
| `entries`        | 是       | array             | 对象和数量。同一 record 内的 `id` 必须唯一。                                                       |

`record_id` 一经发送不得复用。接收方处理规则：

- 首次看到：正常处理。
- 已存在且正文相同：作为重复提交成功返回，不再次修改库存。
- 已存在但正文不同：返回 `record_conflict`。

幂等范围是目标用户；不同用户提交相同 `record_id` 互不影响。

接收方比较正文时直接比较协议业务字段，不要求生产者提供哈希。

## 5. Entry 字段

```json
{
  "id": "char_105_simahui",
  "name": "司马徽",
  "count": 2
}
```

| 字段    | 必填 | 类型    | 说明                                             |
| ------- | ---- | ------- | ------------------------------------------------ |
| `id`    | 是   | string  | operators.json 中的稳定 ID；这是跨平台身份主键。 |
| `name`  | 否   | string  | 当前展示名称，便于人工阅读，不作为主键。         |
| `count` | 是   | integer | 数量。取值规则由 `record_type` 决定。            |

身份主键始终为 `(entity_type, id)`：`item` 使用 `agent/items.json` 的 `id`，`agent` 使用 `agent/operators.json` 的正式 `id`（例如 `char_105_simahui`）。合作平台必须维护自身 ID 到这套稳定 ID 的映射，不能只靠中文名匹配，因为名称可能改名、存在别名或发生本地化。角色识别模板所用的拼音 `item_id` 不是跨平台角色 ID。

当 `id` 有效但 `name` 与当前目录不同，接收方应以 `id` 为准并可返回 warning；未知 `id` 应返回 `unknown_entity_id`，不能按名称猜测。

### 5.1 对象目录交换

合作平台可以直接根据 MaaYuan 发布的 `agent/items.json` 与 `agent/operators.json` 建立映射，也可以使用后端提供的目录接口：

```http
GET /v1/inventory/catalog
```

推荐响应：

```json
{
  "format": "myshare-entity-catalog",
  "version": 1,
  "catalog_version": "2026-08-16",
  "entities": [
    {
      "entity_type": "agent",
      "id": "char_105_simahui",
      "name": "司马徽"
    },
    {
      "entity_type": "item",
      "id": "baijinbi",
      "name": "白金币"
    }
  ]
}
```

现有平台可以保留自己的内部 ID，只需在导入导出边界转换为 MyShare 规范 ID。

## 6. 两种记录的语义

### 6.1 `reward_delta`

表示一次真实奖励产生的增量：

```json
{
  "record_id": "myshare:7f75b99e98834590a0aca3634e8fab5d",
  "record_type": "reward_delta",
  "entity_type": "item",
  "effective_at": "2026-08-16T10:10:00+08:00",
  "entries": [{ "id": "baijinbi", "name": "白金币", "count": 5 }]
}
```

规则：

- `count` 是正增量，必须为 `1..2147483647`。
- 缺少某对象表示本次没有该对象，不表示 0。
- 相同对象在一次识别中出现多次时，发送前合并求和，`entries` 内不得重复 ID。
- 流水用于时段统计；只有奖励时间晚于相应库存快照基线时，才增加当前库存。

协议 v1 不使用负数修正。错误记录由平台管理接口撤销或更正，不能发送相反数伪装成奖励。

### 6.2 `stock_snapshot`

表示绝对库存值：

```json
{
  "record_id": "myshare:stock:2f38fa436d204449bcbf3ac395a6e275",
  "record_type": "stock_snapshot",
  "entity_type": "item",
  "effective_at": "2026-08-16T10:30:00+08:00",
  "snapshot_scope": "listed",
  "entries": [{ "id": "baijinbi", "name": "白金币", "count": 103 }]
}
```

规则：

- `count` 是绝对值，必须为 `0..2147483647`。
- `full`：正文是该类型的完整库存；未列出的对象视为 0。允许空 `entries`，表示该类型全部为 0。
- `listed`：只覆盖列出的对象，未列出的对象保持不变；必须至少包含一个 entry。
- 只有确认完成整个背包扫描时才能发送 `full`。屏幕上只识别了一页或一部分时必须使用 `listed`。
- 该快照之前的奖励仍可用于历史统计，但不再参与当前库存计算。

## 7. 时间、顺序与延迟上传

- 所有时间使用 RFC 3339，例如 `2026-08-16T10:30:00+08:00` 或 `2026-08-16T02:30:00Z`。
- `effective_at` 必须是游戏数据实际发生/读取时间，不能用之后的导入时间代替。
- 接收方必须先验证整份文档，再按 `effective_at` 升序应用 records。
- 相同时间先应用 `reward_delta`，再应用 `stock_snapshot`；即同一时间的快照拥有最终权威性。
- 延迟到达且 `effective_at` 不晚于库存基线的奖励只保存为历史流水，不增加当前库存。
- 统计时间区间使用 `[from, to)`，由查询方明确时区。

## 8. 导出模式

平台应至少支持“当前状态导出”：

- 每个 `entity_type` 生成一条 `full` `stock_snapshot`。
- 适合迁移、备份和导入合作平台。
- 不需要附带历史奖励流水。

如果用户选择“包含历史统计”，再附带指定时间范围内的 `reward_delta`。导入后：

- 快照决定当前库存。
- 奖励流水决定历史获得量。
- 快照之前的流水不会再次增加库存。

平台不得导出由旧快照加全部历史奖励重新计算出的库存；应导出自身当前保存的绝对库存。

## 9. HTTP 绑定建议

### 9.1 导入

```http
POST /v1/inventory/import
Content-Type: application/json
Authorization: Bearer <token>
```

请求正文就是本协议的完整 JSON 文档。

成功响应示例：

```json
{
  "accepted": 2,
  "duplicates": 1,
  "history_only": 0,
  "superseded": 0,
  "warnings": []
}
```

重复 records 属于幂等成功。整份文档格式不合法时不应部分写入。

### 9.2 导出

```http
GET /v1/inventory/export?include=current,rewards&from=2026-08-01T00:00:00%2B08:00&to=2026-09-01T00:00:00%2B08:00
Authorization: Bearer <token>
Accept: application/json
```

返回正文仍使用本协议格式，因此 API 导出文件可以原样上传到另一个兼容平台。

### 9.3 错误正文

```json
{
  "error": {
    "code": "unknown_entity_id",
    "message": "Unknown item id: future-item",
    "record_id": "partner-a:1234",
    "entry_id": "future-item"
  }
}
```

推荐状态码：

| HTTP    | code                         |
| ------- | ---------------------------- |
| 400     | `invalid_json`               |
| 401/403 | `unauthorized` / `forbidden` |
| 409     | `record_conflict`            |
| 422     | `schema_validation_failed`   |
| 422     | `unknown_entity_id`          |
| 422     | `unsupported_version`        |

## 10. 版本兼容

- `version` 是协议 major version。
- 接收方必须拒绝不支持的 major version。
- v1 接收方应忽略不认识的可选字段，但不得忽略不认识的 `record_type`、`entity_type` 或 `snapshot_scope` 枚举值。
- 新增可选字段不提升 major version；改变现有字段语义、删除必填字段或新增必填字段时提升 major version。
- `catalog_version` 与协议版本独立；目录新增对象不需要升级协议。

## 11. MaaYuan/MyShare CSV/JSONL 转换

MaaYuan 当前识别报告按成功格子逐行记录。转换为协议时：

1. 按 `invocation_id` 分组。
2. 取该组 `timestamp` 作为 `effective_at`。
3. 按 `entity_type` 拆分为不同 record。
4. 普通道具以 `item_id` 为规范 ID；角色以 `operator_id` 为规范 ID。按规范 ID 分组并对 `count` 求和。
5. `record_id` 使用 `myshare:<invocation_id>`；若同一 invocation 同时含两种类型，分别使用 `myshare:<invocation_id>:item` 和 `myshare:<invocation_id>:agent`。
6. 普通道具的 `item_name`、角色的 `operator_name` 写入可选 `name`。
7. 派遣/寿春奖励生成 `reward_delta`；背包读取生成 `stock_snapshot`。

以下字段不导出：

```text
mode, slot, row, column, count_score, count_raw,
coarse_score, match_score, match_scale, refined,
cell_box, match_box, item_center, count_box, index_path
```

## 12. 合作平台接入检查

合作平台完成以下内容即可声明兼容 v1：

1. 能生成和读取 UTF-8 JSON。
2. 能区分 `reward_delta` 与 `stock_snapshot`。
3. 使用 `(entity_type, id)` 识别对象，并维护目录映射。
4. 使用 `record_id` 实现幂等；重复导入不重复增加库存。
5. 正确实现 `full` 与 `listed` 快照语义。
6. 保留 `effective_at`，并正确处理晚于/早于快照的奖励。
7. 导出结果能够通过 v1 JSON Schema 和语义校验。
